## 09:00 — S5 unblocked on O2: the Sep-18 mass cancellation root-caused

**Goal.** Find out why S5 run `20260918-130255_88ba1bd` (`head_to_head_comparison`, 6 arrays,
134 tasks) died three seconds after starting, and get the study running.

**What happened.**

1. **The Sep-18 diagnosis in this repo's notes was wrong.** That entry attributed the failure
   to the inherited-`module` mechanism. `sacct` had already refuted it and it was misread:
   `CANCELLED by 0` (root) with `ExitCode 0:0` means the script never errored, whereas a
   failed `module load` under `set -e` would give `FAILED` with a non-zero code and a
   non-empty `.err`. There were **zero** `.out` and `.err` files.

2. **Real cause: `sbatch --export=ALL,KEY=value`.** O2 cancels the batch step by root within
   1–3 s — `.extern` completes, `.batch` cancelled, `ExitCode 0:0`, `Reason None`, no output
   at all. Isolated by submitting one payload five ways on three nodes: the combined form
   cancelled every time; plain `--export=ALL` and no `--export` completed; shell-exported
   variables plus plain `--export=ALL` completed **and** delivered the variables. Ruled out
   independently: script-file vs `--wrap`, output to subdirs and to `/n/scratch`, `--mem=2G`,
   `module load`, outbound `curl`, node health, account standing.

   `launch_subset.sh:152` used exactly this form, as did the scaffold it came from.

3. **A second, independent defect, found only by trying to submit.** `launch_subset.sh` runs
   on a login node and calls `Rscript` in its preflight. `module` is a bash function Lmod
   `export -f`s into the environment, so it is inherited — present for a human at a prompt,
   absent under `ssh host 'bash -s'`. The existing `if command -v module` guard silently
   skipped because `module` was *undefined*, not unloaded, so agent-driven submission died at
   `Rscript: command not found` while the same command worked when typed by hand. Fixed by
   sourcing `lmod.sh` before strict mode, then loading the toolchain.

4. **S5 R1 runs.** Array `54215944`: all 5 tasks `COMPLETED 0:0` (7:50–14:54, MaxRSS ~350 MB
   against 4 G), 5 shards, **zero** non-empty `.err`,
   `1000 reps x 5 arms = 5000 rows, 0 failed rep(s)`, `finished with status 0`.

5. **Two O2 facts settled in passing.** Compute nodes **do** have outbound egress
   (`curl` → 200), and `--mail-type` works (completion mail arrived). Both were open
   questions for the unattended-pipeline design.

6. **`run_simulations.slurm`, `profile.slurm`, `resize_sizing.R`, `submit_per_method.sh`,
   `submit_tier2.sh`, `smoke_autosubmit.sh`** all carried the fatal export form or the
   missing bootstrap; all fixed, committed and pushed to GitHub (`5d71a5c`).

**Decisions.**
- Instruction text counts. `resize_sizing.R`'s `stop()` messages and `profile.slurm`'s header
  comments *told the reader to run the fatal command*; reworded to `VAR=value sbatch
  --export=ALL …`.
- `prep_offline.sh`-style nested `sbatch` inside a `--wrap` string was hand-edited rather
  than machine-transformed — two levels of escaping, and a corrupted quote would reproduce
  the same zero-output cancellation it was fixing.

**Mistake worth recording.** The first attempt to reconcile O2 with git left the checkout
**worse**: I discarded the hand-written fixed files expecting `git pull` to replace them, but
the pull aborted on unrelated uncommitted O2-local edits (`common.R` in three studies), so O2
briefly sat at `88ba1bd` with the *old broken* versions. Repaired by stashing the blockers and
pulling to `5d71a5c`, verified live (`bootstrap:2`, `fatal-form(exec):0`). The stash proved
redundant — all four `common.R` files were byte-identical to what git already had. Lesson:

## 11:00 — S5 sweep submitted (R1–R6); R3/R4/R6 hit a NEW crash, not the Sep-18 one

**Goal.** Combine R1, submit the remaining regimes, and confirm the whole S5 sweep is healthy.

**What happened.**

1. Pulled O2 to `5f7d0a8` (docs-only diff, no code change), combined R1 for real (4 cells,
   5000 rows each, 0 failed reps). Submitted R3/R4/R6 (cheap regimes) as run
   `20260923-092716_88ba1bd`, then R2/R5 (the expensive, crossfit-heavy regimes) once the sizing
   table confirmed the 3× safety-factor walltime absorbs R1's ~2× pilot-projection miss.
2. **A ~10-15 min check-back found real failures, not queue wait**: R3 28/28 tasks FAILED, R4
   3/3 FAILED, R6 4/12 FAILED — all `exit 134` (SIGABRT) within 4-9 s, all before any
   checkpoint flush. R2's first 6/48 tasks failed the same way; tasks 7+ and all of R5 ran
   clean. This is a **different bug** from the Sep-18 mass cancellation (that was
   `CANCELLED by 0`/`ExitCode 0:0` with zero output; this is `FAILED`/`134:0` with a real
   `.err`).
3. Every `.err` for the failing tasks carries the identical signature:
   ```
   free(): invalid pointer
   .../slurm_script: line 104: <pid> Aborted (core dumped) Rscript ...
   ```
   — glibc heap corruption, not an R-level condition (R's own `tryCatch` in
   `run_one_rep(on_error="record")` already handles the sibling "model has no trees" case
   gracefully; this bypasses it because a native abort kills the whole process).
4. **Root-caused the call path, not yet the exact line.** `estimate_att()`/
   `estimate_att_crossfit()` → `optimaltrees::bisect_lambda_to_budget()`/`fit_tree()` →
   Rcpp → `GOSDT::fit()`, which spawns a real `std::thread` even at `worker_limit=1`
   (unconditional `workers.emplace_back(...)` in the loop). Captured a **live gdb backtrace
   on O2** (core dumps land in the compute node's local `/var/spool/slurmd/jobNNNN/` and are
   gone by the time the job exits, so post-mortem core analysis doesn't work — had to
   reproduce under `gdb -batch -ex run -ex "bt full"` directly):
   ```
   #4  malloc_printerr  #5 _int_free  #6 free
   #7  shared_ptr<Bitmask>::_M_dispose  ...  #13 Model::~Model (model.cpp:127)
   #14 Optimizer::models (models.hpp:32 -- inlined single_model())
   #15 GOSDT::fit_gosdt  #16-18 GOSDT::fit -> treefarms_fit_with_config_cpp
   ```
   Crash is AFTER the worker thread is joined (single-threaded model extraction), so it is
   **not a live data race** — it's a genuine heap-corruption bug, most likely a double-free
   or use of a corrupted `Bitmask` inside `Optimizer::single_model()`
   (`src/optimizer/extraction/models.hpp`, added 2026-09-08 commit `140d110`, the
   deterministic single-tree extraction that replaced the old tied-tree-enumeration path).
5. **Two rounds with Oracle + direct source reading refuted every specific mechanism tried**:
   `Task&` dangling across `single_model()`'s recursion (refuted — `unordered_map` reference
   stability across rehash is guaranteed by the standard, and nothing erases from
   `state.graph.vertices` during extraction), missing NSDMIs on `Bitmask` members (refuted —
   they're all present and correct: `content = NULL`, `shallow = false`, etc.), a shallow
   `Bitmask` copy constructor (refuted — it's a genuine deep copy via `initialize()` +
   `memcpy`), `Dataset::subset()` resizing past capacity (refuted — it's pure in-place
   `bit_and`, never resizes). What's confirmed: the crashing `Model` is a **leaf** (internal
   nodes never populate `capture_set`, so only a leaf's `shared_ptr<Bitmask>` destruction can
   reach `free()`), and the bad `Bitmask` traces to one of the three `new Bitmask(...)` call
   sites inside `single_model()` — root cause not yet pinned to an exact line.
6. **Could not reproduce locally at all**, despite exhaustively matching conditions: same
   `optimaltrees`/`doubletree` git SHAs, the exact 3 crashing (regime, dgp, n) configs swept
   300+ replications, plus 50 concurrent processes under heavy CPU oversubscription (10-core
   Mac) to simulate O2's contention. Zero crashes on macOS ARM64/Apple-clang/libSystem-malloc.
   Oracle's read: consistent with genuine platform-independent UB that glibc's stricter
   `free()`-time consistency checks catch and macOS's allocator doesn't detect — not evidence
   the bug is Linux-specific in cause, just in *detection*.
7. **Attempted an ASan-instrumented rebuild on O2** to settle it properly; got the build
   compiling and linking with `-fsanitize=address`, but lost the round to O2-specific
   infrastructure snags rather than getting a memory-error report: (a) `R CMD INSTALL` on this
   O2 R setup defaults to `/home/dma12/R/library/4.4`, which is **not even in `.libPaths()`**
   — the real production path is `/home/dma12/R/x86_64-pc-linux-gnu-library/4.4` and needs an
   explicit `--library=`; (b) an ASan-instrumented `.so` cannot be `dlopen`'d into a host
   process that didn't itself start with `LD_PRELOAD=libasan.so` — R CMD INSTALL's own
   "testing if installed package can be loaded" self-check fails for exactly this reason and
   needs `--no-test-load`; (c) a 3-config sequential capture run got killed by an outer
   timeout before reaching the revert step, briefly leaving the **production package
   uninstalled**, then reinstalled but only loadable under `LD_PRELOAD` (broken for any normal
   task). Reverted and verified clean (`library(optimaltrees)` loads with 0 ASan symbols) —
   no impact on the sweep: R2/R5 had already finished before any of this, and the two
   unrelated jobs seen running in `squeue` at the time (`validation`, `orthogonal-objective-sim`)
   had already loaded the package into memory before it was touched.
8. Also root-caused (separately) why local native-code experimentation stalled for a large
   chunk of this session: **ThreatLocker** blocks locally-compiled `.so` files from loading
   (`dlopen(...) -> mmap ... errno=1`), confirmed both by a colleague's independent report
   (Rcpp-dependent CRAN installs blocked, `type="binary"` as a workaround) and by reproducing
   with a trivial, previously-never-compiled 2-line `Rcpp::sourceCpp()` snippet. Full writeup:
   `~/RAND/tools/opencode-omo-setup/incidents/2026-09-23_threatlocker-blocks-local-rcpp-compile/README.md`.
   The colleague's `type="binary"` fix does not apply to local package development (nothing to
   fetch instead of compiling) — needs an IT-side ThreatLocker path/publisher exception.

**Decisions.**
- Not a "major refactor" of `optimaltrees`. The pieces actually read (`Bitmask` copy/dtor/
  `operator=`, `Model`'s constructors) are individually correct; the bug is scoped to one new
  code path (`single_model()`, ~2 weeks old) plus, per Oracle, a Rule-of-Three audit of
  `Bitmask` is a small (~1-file) widening worth doing regardless of what the exact mechanism
  turns out to be.
- Regression coverage for this needs to run on Linux (or at minimum under ASan, which Oracle
  suggested might reproduce even on macOS — not yet tried, since macOS is currently blocked by
  ThreatLocker anyway).

**Mistake worth recording.**
- Ran a multi-config ASan capture as one long foreground SSH call with a fixed timeout and no
  revert-first ordering. When the outer timeout fired mid-run, the revert step (needed to
  restore the loadable-without-`LD_PRELOAD` production build) never ran, and a second attempt
  hit the same problem via a `set -e` diagnostic check that itself errored out before reaching
  the revert. Fixed by moving the revert to the FRONT of the recovery script and dropping
  `set -e` around anything expected to fail. Lesson for next time: launch each ASan capture as
  its own backgrounded (`nohup` + poll), single-config call, and never combine "capture
  evidence" with "restore safety" in one script where the first can eat the timeout budget the
  second needs.
