## 11:20 — correction: `diagnostics` is a reported flag, not an estimator fallback

**What was wrong.** The first pass above, and the code/docs it produced, drifted into framing the
resolved `diagnostics` rule as licensing a *substitution*: "when the licence fails, report
`estimate_att_crossfit()` instead of `estimate_att()`." The PI corrected this directly: **"we
never fall back to cross-fitting. No silent fallbacks."** That framing contradicts
`07_estimate_att.R`'s own pre-existing, unchanged design (stated in its header before today):
`estimate_att()` is always the flagship (per `config_estimator`), `estimate_att_crossfit()` is
always its companion, both are always reported alongside their discrepancy, and the script never
auto-switches between them — auto-switching would be the data-dependent post-selection inference
the paper does not analyse. My printed "Licence FAILS" message and the `_config.R`/README prose
had reintroduced exactly the fallback the file's own header disclaims.

**Fix.** `certified_e && certified_m0` is a **reported diagnostic flag on the flagship result**,
nothing more: it says whether this proxy supports grid-exact sparsity for `estimate_att()`. It
does not change which number is "the" estimate, does not trigger any substitution, and a failed
licence is a signal to scrutinize `07`'s already-reported discrepancy in the write-up — not an
instruction to swap in `estimate_att_crossfit()`'s number. Reworded the licence-print block in
`07_estimate_att.R`, the `note` in `application/_config.R`'s `diagnostics` entry, `07`'s header
comment, and the `README.md` decision-table row accordingly. Re-parsed all four `.R` files and
re-ran `application/run_tests.R` — unchanged 192 passed / 4 failed (the pre-existing
`optimaltrees.so` block, confirmed via `git stash` comparison, both before and after this
correction).

## 15:40 — `estimate_att()` paper/code alignment audit + fix

**Goal.** PI: "we've changed the paper to do L2 loss for both e and mu... need to talk about how
to set lambda appropriately... make sure other explicit assumptions (leaf floor) are enacted in
the package... determine if we need to re-run simulations." Full audit of `estimate_att()` (the
theory-proven flagship) against `theory.tex`, then rock-solid package defaults, then implement.

**Scope, per PI instruction mid-audit:** de-prioritize `estimate_att_rashomon()` entirely (not in
the paper) and `estimate_att_crossfit()` (Part I, "not the most important... could use another
anchor") — full rigor on `estimate_att()` + its direct `optimaltrees` dependencies only; light
sanity pass on crossfit (confirm not actively broken, no deep theoretical work).

**Method.** Three parallel `explore` passes (theory.tex's actual loss/leaf-floor/lambda_n
specification with exact proof citations; the R+optimaltrees implementation map; a
`simulations/` staleness inventory) → two Oracle consults (first: initial gap analysis; second,
after the PI questioned two specific findings and asked "do we have rock solid evidence loss
matters" — two more `explore` passes re-examined (a) whether the paper's `R^(mu)_n` really needs
to average over full `n` vs `n0` controls [answer: yes, load-bearing, quoted directly from
`lem:selection`'s Step 1 proof, not a notational slip] and (b) whether
`simulations/propensity_loss_choice`'s existing loss-comparison evidence is confounded [answer:
yes, confirmed — same shared, scale-blind `lambda_n` gives squared_error ~1.45x more relative
bite than log_loss under log_loss's own root-loss scale, independent of which loss is actually
better] → a third Oracle consult for the final, itemized package-default list) → implementation
→ real `R CMD INSTALL` of both `doubletree` and `optimaltrees` from source (not `devtools::
load_all()`, which is blocked locally — see below) → full test-suite verification → commit.

**What shipped** (`doubletree` `9d712b0`, `optimaltrees`/treefarmr `252fbdb`, both pushed):

- `propensity_loss` default → `"squared_error"` (was `"log_loss"`); outcome-tree loss now
  unconditionally `"squared_error"` regardless of `outcome_type` (was conditional) —
  `ass:construct(a)`: "Both nuisances are fitted by squared error." Required a same-commit
  companion fix in `predict_nuisances_fold()` (branch on the model's own `@loss_function`, not
  `outcome_type`, for the m0 prediction call — mirrors the e-branch's existing pattern; without
  it, a "binary" `outcome_type` with a now-squared_error-fit m0 model hard-aborts).
- `lambda_n` read as a fraction of each tree's own root-node loss (`lambda_n * L_root`), not
  passed absolute. Fixes the real-data hang's primary mechanism (a shared `log(n)/n` is
  functionally zero against a dollar-scale mu-tree) *and* a confirmed confound in
  `propensity_loss_choice`'s existing loss-comparison evidence (same bug, different symptom) —
  **that ablation's conclusions should not be trusted until re-run under this fix.**
- `m_n` default `1L` → `NULL`/`ceiling(sqrt(n))` — `eq:feasible` imposes a rate, not a value; the
  old default was vacuous (confirmed: 35.7% clip rate in `propensity_loss_choice`'s weak-overlap
  cell at `m_n=1`).
- Clipping: one-sided now (new `clip_c` param, default `0.01`), was two-sided. `theory.tex`:
  "$e_0(x)=0$ is harmless"; two-sided clipping forfeits the one-sided clip's non-expansiveness
  "wherever $e_0 < c$." New `clip_rate_e` diagnostic (motivated by `rem:clip-margin`).
- `any_truncated_e`/`any_truncated_m0` now surfaced (already computed by
  `bisect_lambda_to_budget()`, just not returned) — closes the gap where `certified_*` could
  show a false green light on a truncated search.
- `outcome_type` reverse-warning added (continuous declared, Y actually binary).
- `optimaltrees::bisect_lambda_to_budget()`: dropped the scale-blind `hi_init` absolute floor
  (`max(2*lambda_n, 0.01)` → `2*lambda_n`; the `0.01` dominated whenever `lambda_n` was small in
  absolute terms — exactly the e-tree's own case even *after* the root-loss fix, traced with
  real arithmetic at n=227,309); bracket `lo` now tightens using rejected-`hi` values instead of
  staying pinned at `lambda_n`; early-exit once the bracket is tight (`hi/lo < 1.05`).

**Confirmed NOT a gap, no change:** the leaf-mass floor's control-count mechanism for the

**A real bug found and fixed along the way, not introduced by this session's changes:** one
existing test (`test-propensity-loss.R`, "errors rather than silently misreading a misrouted

also break for that exact fixture. The scenario (manually corrupting `@loss_function` post-fit)
is not reachable through any real doubletree call path — fixed the test to lock in the honest,
documented current behavior instead of a defense that never actually existed, and corrected the
now-proven-false roxygen claim in `nuisance_trees.R`.
